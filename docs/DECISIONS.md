# Design decisions

Binding architectural and process decisions. Append rows at the end (append-only) — parallel
lanes then merge trivially. Record a decision in the same PR in which it takes effect.

| Date | Decision | Rejected alternatives | Rationale |
|---|---|---|---|
| 2026-09-17 | The plugin was developed inside the owner's private project repository and imported here as release 0.2.0 in a single commit; its earlier history stays private | `git subtree split` with full history | Squash merges had left only a few aggregate commits for the plugin, and the private repository's name must not appear in public history |
| 2026-09-17 | Repository is public, licensed MIT | private repository; Apache-2.0; no licence | The project is meant to be shown and installed from outside; MIT is the simplest permissive licence for developer tools |
| 2026-09-17 | Layout: plugin in `plugin/`, marketplace `wcz-tools` in `.claude-plugin/marketplace.json` at the root with `"source": "./plugin"` | plugin at the root with `"source": "./"` | Project files (`CLAUDE.md`, `docs/`, `scripts/`, CI) live at the root; with `./` they would land in every installer's plugin cache |
| 2026-09-17 | Releases are tagged with `claude plugin tag` (`pipeline--vX.Y.Z`); the version grows with behaviour, not with docs or tests; the owner pushes tags | untagged `main`; version bump on every change | Consumers and rollbacks need stable references; the tag format is the one Claude Code tooling understands |
| 2026-09-17 | Consumers install the marketplace from git over HTTPS (`{"source": "git", "url": "https://github.com/wojciechczarnecki/agentic-pipeline.git"}`) | `github` source (SSH) | The repository is public: background updates need no SSH key or agent, and the README instruction works for anyone |
| 2026-09-17 | Sessions working on this repository use the released plugin from GitHub, not the working tree (`directory: "."`) | `directory` source pointing at this checkout | A stable release guards work on unstable code; with the working tree the guard would also block shell writes to `plugin/` |
| 2026-09-17 | Dev tools (ruff, black, pytest) pinned in `pyproject.toml` `[dependency-groups] dev` with `uv.lock` committed; the plugin keeps zero runtime dependencies | `uvx` without a lock | Reproducible CI and Dependabot updates; hooks run on plain `python3` in any consumer |
| 2026-09-17 | Project documents are in English (`language: "en"`); skills, agents and `plugin/README.md` stay in Polish until translated (`docs/BACKLOG.md`, P2) | Polish project documents; translating in the import | Public repository; `language` is independent of the skills' language, and the import must not change behaviour |
| 2026-09-17 | CI runs `claude plugin validate --strict` for the plugin and the marketplace, ruff, black and pytest on every PR; `claude plugin eval` is manual only | eval as a PR gate | Eval runs a real model: cost, variance and a secret |
| 2026-09-17 | Sessions in this repository pin the `wcz-tools` marketplace to the release tag (`"ref": "pipeline--v0.2.0"`); the pin moves with each release; the declaration alone is inert until the marketplace is re-registered with that `ref` (`CLAUDE.md`), because an entry registered without one keeps tracking `main` | the unpinned source, tracking `main` | Without `ref` every merge here changed the skills and the guard of the next session in this very repository — the opposite of working on the released plugin |
| 2026-09-17 | GitHub rulesets (`main`: pull request, squash only, green `plugin` check, no deletion or non-fast-forward; `release tags`: `refs/tags/pipeline--v*` immutable) with no bypass actors hold for everyone; creating a new release tag and merging a PR are **not** covered by them (no `creation` rule, zero required approvals) and rest on the command guard and the `deny` list alone | classic branch protection; local hooks alone | Hooks are bypassable (`--no-verify`, a fresh clone without `core.hooksPath`) and the guard only sees the agent's own session; the server-side rule holds for everyone |
| 2026-09-20 | The guard's migration module recognises only Alembic's verbs (`upgrade`, `downgrade`, `stamp`, `revision`, `current`, `check`) and the variables `ENVIRONMENT`, `DATABASE_URL`, `DB_HOST`; only `migrations.command` and `migrations.localHosts` are configurable, and the module is deliberately not generalised | configurable verbs and variables; dropping the module | The owner uses Alembic; an honest limitation beats an abstraction nobody exercises. Generalisation stays in `docs/BACKLOG.md` under Guard, trigger: the first consumer using another migration tool |
| 2026-09-20 | `claude plugin eval` is run locally, on demand; the `Plugin eval` GitHub workflow is deleted rather than kept dormant | a manual `workflow_dispatch` workflow; keeping it unrunnable | The API console is a separate account and separate billing from the Claude Code subscription, and the owner will not pay for metered credits on top of the plan. A workflow that cannot run is worse than none: it reads as coverage that does not exist. The local command is in `docs/CONVENTIONS.md`; the eval needs a sandbox backend (`bubblewrap`, `socat`), without which every run is refused at `turns: 0` while the LLM grader still votes FAIL and bills for it |
| 2026-09-20 | The question cap of `/pipeline:init` is not covered by an eval; the `init-question-cap` case is deleted rather than kept red | rewriting the case for the non-interactive path; leaving it failing | `AskUserQuestion` does not exist inside an eval run — a headless run has nobody to ask — so a case whose subject is "one round, at most four questions" can never pass, however well the skill behaves. Measured 2026-09-20: the skill correctly took its non-interactive path and said "0 rounds, 0 questions", which the grader must score as a failure. `init-without-questions` already covers that path. A suite that cannot go green stops being a signal |
| 2026-09-20 | A minor or major release tag is gated on a green local eval receipt (`plugin/evals/last-run.json`, written by `scripts/eval.sh`) checked by the `pre-push` hook; patches are exempt | prose in `docs/CONVENTIONS.md`; gating every tag; a CI gate | A rule nothing checks is not followed — the lesson of SPEC 001. The `release tags` ruleset has no `creation` rule, so the server accepts any new tag and the local hook is the only layer that can bite. The hook compares `plugin/` between the receipt's commit and the tagged one rather than the shas, because the receipt ships inside the release it certifies. Patches stay exempt: a full suite costs about $1.4 and a patch is usually a hook or a documentation fix |
| 2026-09-21 | Stage skills call the metrics checker through `PATH` (`workflow_metrics.py --check <spec-dir>`) and consumers allow `Bash(workflow_metrics.py *)`; `${CLAUDE_PLUGIN_ROOT}` stays only where Claude Code substitutes it (skill text read as instructions, `hooks.json`) | `python3 "${CLAUDE_PLUGIN_ROOT}/bin/workflow_metrics.py"` with a matching allow rule (0.3.0) | Permission rules do not substitute `${CLAUDE_PLUGIN_ROOT}`, so the 0.3.0 rule never matched the absolute path the skill expanded to, and a stage subagent cannot answer the resulting prompt: every `--check` stalled and `final-review` apply could never set `done`. The variable is also absent from the Bash tool's shell. Claude Code appends an enabled plugin's `bin/` to the session `PATH`, and a PATH call with a PATH-form rule ran without a prompt. Measured 2026-09-21 on a stub plugin via `claude --plugin-dir … -p`; this reverses the specs/001 PLAN claim that PATH works only inside this repository |
| 2026-09-21 | Consumers follow the `stable` release channel — a branch the owner moves to each new `pipeline--vX.Y.Z` tag — with a single `--scope user` install per machine; `/pipeline:init` and `templates/settings.json` write `"ref": "stable"`, updates are `claude plugin marketplace update` + `claude plugin update --scope user`, and a repository that does not want the plugin disables it with `"enabledPlugins": {"pipeline@<marketplace>": false}`. `stable` is protected by a ruleset (update, deletion, non-fast-forward blocked) whose only bypass actor is the repository Admin role — the owner's account. Moving `stable`, like creating the release tag, is the owner's alone (corrected 2026-09-21): the bypass would let an agent pushing with the owner's credentials set the channel to any commit, and the guard protects `main`/`master` only, so `deny` rules in `.claude/settings.json` matching the `stable` refspec of `git push` (bare, `<src>:stable`, `refs/heads/stable`, quoted) keep agents off it — measured with `claude -p --settings` against a local remote, working branches with `stable` in their name still push. Supersedes the tag pin of 2026-09-17 | pinning `ref` to the release tag with `--scope project` installs | The marketplace `ref` is global per machine (`~/.claude/plugins/known_marketplaces.json`) and `install`/`update` take no version, so a tag pin forced `marketplace remove` on every release — which uninstalls the plugin in every project — and a reinstall in each of them. Measured 2026-09-21 with an isolated `CLAUDE_CONFIG_DIR` and a local git marketplace: registered on `stable`, one `--scope user` install carries no `projectPath` and works in every directory; moving `stable` to a new tag, then `marketplace update` and `plugin update --scope user`, reported "updated from 0.0.1 to 0.0.2" with the registration untouched. Cost: the guard runs everywhere, including repositories that commit straight to `main`, hence the opt-out |
| 2026-09-21 | Projects declare only the marketplace source (`extraKnownMarketplaces`) in `.claude/settings.json` and never `"enabledPlugins": {"pipeline@<marketplace>": true}`; `templates/settings.json`, `/pipeline:init`, both READMEs and this repository follow it. `"enabledPlugins": {...: false}` stays as the only project use of the key — the opt-out | keeping `enabledPlugins: true` so a fresh clone enables the plugin by itself; keeping `--scope project` installs as an option for version isolation | Measured 2026-09-21 with an isolated `CLAUDE_CONFIG_DIR` and a local marketplace: a session started in a directory whose settings enable the plugin installs it at `--scope project` on its own, even beside an existing `--scope user` install, and `claude plugin update --scope user` lifts only the user entry, so the project entry stays on its old version for good — a silent duplicate in every repository, against the single user install per machine. The same directory with `extraKnownMarketplaces` alone creates no project entry and loads the plugin from the user install |
| 2026-09-21 | `plugin/README.md` and `plugin/docs/` are in English ahead of the skills; skills, agents, templates and `plugin/CHANGELOG.md` stay Polish until Stage 8, and the README quotes the literals they produce (`## Decyzje właściciela`, the `RESULT` block) verbatim in code. Amends the 2026-09-17 language row for the README only | translating the README together with the skills in Stage 8; keeping it Polish | The README and `docs/GUARD.md` are what an outside reader meets first, and the guard documentation links from the README's guard section; the skills are behaviour and their translation needs the Stage 5 eval gate, the README does not |
| 2026-09-21 | Push refspecs are resolved like removal paths: expanded with the variables known before the command (session environment, earlier assignments, `export`), with shell semantics — a prefix assignment does not count for the command's own arguments, an empty value disappears, a value splits on whitespace — and refused with "spell the branch out" when anything stays unresolved (unknown variable, `$(...)`, backticks, a conditional assignment); a variable remote with literal refspecs passes | resolving known variables and letting the rest through; expanding with every assignment in sight; expanding inside the tokenizer for every rule | A push cannot be taken back, and `rm` paths and `gh api -X DELETE` endpoints already refuse what they cannot resolve; the guard must judge what the shell runs, so `B=feat/x git push origin $B` and `E=; git push origin $E` push the current branch. Cost: `git push origin HEAD:$(git branch --show-current)` is refused (0.3.4 CHANGELOG) |
| 2026-09-21 | After the final review of SPEC 002 the guard follows a variable only where its value is certain: a subshell, a pipeline command and a background command keep their assignments and `cd`; `bash -c` sees only exported names; an assignment behind `&&`/`||` or inside a control block, one made by an assigning builtin (`read`, `declare`, `unset`, `printf -v` …), an append, an array element and every expansion after an `IFS` change count as unknown. Push options are read after expansion, option values are skipped when the remote is picked, and `--all`/`--branches`, refspec patterns, `heads/main`, push configuration (`remote.*.push`, `remote.*.mirror`, `push.default`) and `git config --edit` are refused | modelling bash exactly (restoring a variable after `if`/`else`, iterating loops); documenting the gaps instead of closing them | Each gap let a command pass on `main` that the shell runs as a push to `main` (measured on the 0.3.4 branch). Treating what the guard cannot follow as unknown costs a refusal in rare constructs (`for …; do D=…; rm -rf $D; done`) and keeps the rule simple to state; an alias already in a configuration file and constructs the guard does not parse stay known limits in `plugin/docs/GUARD.md` |
| 2026-09-21 | Git aliases are refused: `git -c alias.*` and any write of a persistent alias (including `--unset` and a section rename onto `alias`), and a removal or rename of the `core` section counts as a `core.hooksPath` write; reading an alias or `core.hooksPath` passes. Scripts written to files, interpreters, shell functions and git configuration channels the guard does not parse are documented as known limits in `plugin/docs/GUARD.md` and backlogged | documenting aliases only; trying to close every evasion | Aliases are as cheap to block as `-c core.hooksPath` and one parser tells a `git config` read from a write; scripts and interpreters cannot be analysed from a command string, and the guard is best effort by definition, with `pre-push` and the rulesets behind it on `main` |
| 2026-09-21 | `plugin/docs/GUARD.md`'s deny-versus-guard table is parsed by `plugin/tests/test_guard.py` and every command in it is run through the guard; its deny side was measured with `claude -p --safe-mode --settings` in a sandbox repository with a local remote, once without and once with the rule (2026-09-21, Claude Code 2.1.272): 14 of 18 candidates got past their rule and are in the table; `env gh pr merge`, `echo $(gh pr merge 12)` and `B=main; git push origin $B` were caught and are not, and `command git push origin main` could not be measured (the model rewrote it); a control row proved `--settings` took effect | hand-copied cases in `test_guard.py`; deny behaviour inferred from documentation | A document nothing checks drifts (SPEC 001 lesson); `deny` matching is Claude Code's behaviour, not ours, and it does split some compound and wrapped commands before matching — only a measurement shows which |
| 2026-09-21 | `plugin/CHANGELOG.md` is translated into English in release 0.3.4, earlier releases included, and a test keeps Polish out of it outside code spans. Amends the 2026-09-21 row that kept it Polish until Stage 8 | translating only the 0.3.4 section; leaving it Polish until Stage 8 | Like the README, the changelog is documentation for the consumer, not behaviour, so it needs no eval gate; an English README linking to a Polish changelog, and a mixed-language file, both break "no mixing of languages within one document" |
| 2026-09-21 | The project's display name is *Spec-Driven Workflow* (README and document titles, manifest descriptions, the GitHub *About* description); the repository slug stays `agentic-pipeline`, and the plugin name `pipeline` — its `/pipeline:*` commands, the install id `pipeline@wcz-tools` and the `pipeline--v*` tags — is permanent | renaming the slug (`pipeline`, `guarded-spec-workflow`, `spec-driven-workflow`); renaming the plugin now or at Stage 8 | An outside reader meets the display name, the slug appears only in URLs, so the title changes with no URL or consumer impact; a slug rename stays cheap later (GitHub redirects). A plugin rename touches every command reference, the tag prefix and its ruleset, the install id and each consumer's install, and the namespace is typed in every command, so it should stay short. The phrase is shared with other repositories (`spec-driven-workflow`, `claude-code-spec-workflow`, checked 2026-09-21), so the pitch, not the name, carries the difference (SPEC 003) |
| 2026-09-21 | The install guide lives at `plugin/docs/INSTALL.md`, beside `GUARD.md`; `plugin/README.md` and the root `README.md` keep a short install and a link to it | `docs/INSTALL.md` (the roadmap's path) | `plugin/` is what reaches the consumer's plugin cache; `docs/` holds project documents, and a link from `plugin/README.md` into it breaks outside GitHub (SPEC 003) |
| 2026-09-21 | Every release tag gets a GitHub Release titled `pipeline X.Y.Z`, with the matching `plugin/CHANGELOG.md` section as its notes, created by the owner after the tag and the `stable` move with `gh release create --verify-tag`, so the command never creates a tag; the six existing tags are backfilled by the agent after the owner's approval at gate 2 of SPEC 003 | no Releases; notes generated by GitHub from commits | The Releases page is where an outside reader looks for versions, and the changelog already carries the consumer impact; `--verify-tag` keeps creating tags the owner's move, and a Release is reversible |
| 2026-09-21 | Repository rules and repository documents are tested in the root `tests/` (`tests/test_documents.py` beside `tests/test_release_gate.py`), and `scripts/check.sh` and CI run it together with `plugin/tests` | the root-document tests in `plugin/tests` reaching the root with `parents[2]` | `plugin/tests` must run from the plugin alone (`cd plugin && python3 -m pytest tests`); the root `tests/` was not run by CI before, so `test_release_gate.py` had gone unchecked (SPEC 003) |
